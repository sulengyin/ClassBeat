# 13 · 语言分工与架构审查（2026-11-22）

0.5.0 把服务迁到 Rust、0.5.1 补上更新链路之后，"哪个组件该用什么语言"就没人再统一说过
一遍。结果是有三套东西并行：老 Python 形态（zip + pythonw + 看门狗）、Rust 桌面形态、
以及两边都要维护的 JS 前端。这份文档把判定标准写死，逐组件过一遍，并记下这次审查的
发现与处置。

---

## 13.1 判定标准：三条

**① 跑在谁的机器上、失败谁承担。**
跟着安装包发到老师电脑上的东西，必须是"解压即可运行、不依赖外部运行时、体积可控"的：
Rust（静态链接、单 exe）或前端 JS（浏览器自带运行时）。
只在开发机/CI 上跑一次的东西，语言随意，优先用现成轮子——为一次性任务引一整套工具链是亏的。

**② 它是产品，还是尺子。**
产品（老师看得见的行为）**只留一份实现**。
尺子（参考实现、冻结基准、交叉校验）**允许第二种语言**，但必须满足两条：输出被冻住、
每次改动都被测试比对。这样两份实现一旦漂移就报错，而不是悄悄各走各的。

**③ 入口越少越好。**
同一件事有两个入口，就一定有人从错的那个进去。打包、更新、验收都是这样：
老形态和桌面版各有一套更新器、各有一套打包链，维护成本不是加法而是乘法。

## 13.3 发现一：`data.js` 有两份生成器（已加护栏）

`tools-rs/src/bundle.rs` 和 `tools/bundle.py` 做的是同一件事：把 `sample/`（或 `data/`）
的七个 JSON 拼成 `window.RHYTHM_DATA`。这份重复是有原因的——
JS 单元测试与 e2e 的 CI job 里没有 Rust 工具链，而 `stage` 装配必须用 Rust 版。

如果哪天两边漂了，症状是**测试跑的和发出去的不是同一份配置**，极难发现。所以：

- 约定：`generatedAt` 之外必须相同，改动任何一边都要同步另一边；
- **已加硬护栏（2026-11-23）**：`tools/check_bundle_parity.py` 让两边各出一份，
  抹掉首行署名、`generatedAt` 与换行后逐字节比，不一致就报第一处差异并退出 1；
  `ci.yml` 里新增 `parity` job 跑它。护栏本身验过：把 `version` 从 2 改成 3，
  它准确指向第 30 个字符并失败；改回来即通过。
- 顺带修掉一个跨平台隐患：`tools/bundle.py` 以前用文本模式写文件，Windows 上换行
  被翻转成 CRLF，同一份数据在不同平台生成的字节就不一样。现在钉死 LF。

`parity` 只比**结构和取值**，不比顺序之外的排版；如果将来真要分道扬镳，
先改这一节的约定，再删断言——别直接删脚本。

## 13.4 发现二：图标只能用这台机器重生成

`tools/make_icons.py` 是纯 Python、零第三方依赖（自己写的 PNG 读写与 ICO 打包），
这点很好。问题在别处：

- 它**不进任何构建链**，产物（`desktop/src-tauri/icons/classbeat.ico`、
  `server/icons/*.png`）是入库的静态文件，只有换品牌图时才跑一次；
- 所以它不是"产品实现"，而是"素材工具"。这类工具留在 Python 里不算"强行 Rust"，
  真要迁，收益是省掉一次 `python3`，成本是几百行位图代码从零搬。

**2026-11-23：图标收敛成一份源图 + 一个入口。**

- 源图只有 `tools/brand/icon-source.png` 一份，`make_icons.py` 只做"从源图缩放"，
  不再在本文件里画形状（PR #34，13:49）。产物一次出三处：手机页 PWA 图标、
  安装包 ico、`tools/brand/classbeat.ico` 留档。
- 同时删掉 `tools/make_ico.py`。这个文件是事故源头：它**不带参数时会画一个程序化
  贴纸时钟**当占位图（2026-11-17 用品牌图之前的遗留），某次打包顺手跑了一遍无参版本，
  品牌图被静默覆盖，装出来的桌面图标是一个钟。`make_icons.py` 重写后，
  `make_ico.py` 引用的 `build` / `png_bytes` 已经不存在，留着就是一颗随时 ImportError
  的死代码，更别提它的默认值还会误导人。

教训：**素材工具的默认行为不该指向一个废弃产物**。产物入库、生成过程又不在流水线里，
被误跑一次就无声无息地污染发布物。现在只有一个入口，且这个入口只做一件正确的事。

## 13.5 发现三：老形态其实是第二套产品（已退役）

退役前它是这样一套东西：

| 部分 | 行数 | 只在老形态里存在 |
|---|---|---|
| `server/*.py`（服务 + 守护 + 页面内更新器 + 清单） | 2,752 | 是 |
| `tools/package.py`（zip / 单文件 / 免安装 Python / .bat 生成） | 708 | 是 |
| `tools/build_installer.py` + `tools/installer/`（7zSD 自解压） | 310 | 是 |
| `tools/make_update.py`（老 `update.json` 清单） | 214 | 是 |
| `tools/launcher/*.ps1` + `.cmd`（kiosk / 看门狗 / 自启 / 逃生门） | 1,504 | 是 |
| `tools/smoke_windows.py` + `test_server` / `test_package` / `test_updater` / `test_update_manifest` | 1,810 | 是 |
| `desktop/scripts/*.py`（0.4 迁移期的等价性证据脚本） | 1,130 | 是 |
| 合计（含 `update.json`、`equivalence_probe.cjs`、旧 ico） | **约 8,700 行 / 29 个文件** | |

代价不只是行数：

1. **两套更新器**。桌面版走 `tauri-plugin-updater` + minisign；老形态走"页面里点检查更新 →
   服务下载 zip → 白名单替换 → 健康检查 → 回滚"。两套互不认识对方产物，0.3.x 的"跨代自愈"
   就是在这上面打仗。
2. **CI 每次都下载 11 MB 免安装 Python**，还要 `pip install py7zr` 打自解压包。
3. **自解压 exe 是杀毒误报的常客**——而这个 11 MB 的 exe 只为了让老师省一次"安装"。
4. 改一条作息规则，要在 Python 与 JS 两边同步；改一个卡片样式，要跑三条测试链。

处置（本次已执行）：

- 删除上表全部文件，`release.yml` 的 `package` job 与 `smoke.yml` 的 `windows-smoke` job 一并去掉；
- 「不装软件也能看」这个需求**没有丢**：单文件演示版改由 `classbeat-tools single` 出
  （Rust，复用同一份数据打包逻辑），打标签时和安装包一起挂到 Release；
- 「服务」的回归不再靠 Python 测试：桌面侧的 `verify`（装配不变量）+ `accept`（运行期 17 项）
  接过来，e2e 也从"起 Python 服务"改成起 `classbeat-server.exe`——测的就是发出去的那个二进制。

副作用（如实记录）：`test_server.py` 里那 696 行针对 Python 服务端点的断言（消息长度、
撤回窗口、端口顺延、路径穿越）**没有等价物**。其中一部分由 `accept` 与 e2e 覆盖，
但"用 30 种畸形请求试端点"这类用例确实没了。这是退役必然的损失，记在这里而不是假装没有。

## 13.6 发现四：核查"有没有强行用 Rust 的地方"

逐条看过，**没有**发现"该用脚本却硬写成 Rust"的组件。三个容易被怀疑的地方：

| 位置 | 看起来像"强行 Rust"？ | 结论 |
|---|---|---|
| `tools-rs/src/accept.rs`（566 行）用 Win32 枚举窗口、量窗口尺寸、杀进程 | 像。这些用 PowerShell 十行就能写 | 但它验的正是"壳在真机上的行为"：全屏、误关后自愈、单实例、托盘退出。用 PowerShell 写等于"用被测对象的同族工具验它"，而且 `accept` 要在一台干净机器上跑，不该假设有 PowerShell 环境。留在 Rust |
| `server-rs/src/pyjson.rs`（223 行）复刻 Python `json.dumps` 的格式 | 像。Python 都退役了还留着它干嘛 | 它的另一半职责是**确定性序列化**：备份包按"排序 + 紧凑分隔符"算哈希做去重，格式一变老备份就对不上。所以不能直接换 `serde_json`。**已改口（2026-11-23）**：模块文档现在写的是"确定性 JSON 序列化"，Python 的形状只是既定格式的来源与理由，不再是它的身份 |
| `tools-rs/src/stage.rs` 装配资源、写 `build-info.json` | 这些事 `xcopy` + 一个 ps1 也能干 | 它同时承担"装配不变量"（不许有 `.py`、版本双轨必须一致、资源齐全），和 `verify` 是同一套断言的两端。分开写必然漂 |

反过来，"该用 Rust 却还用脚本"的地方，本次清完了：单文件打包已从 `tools/package.py` 搬到
`classbeat-tools single`；桌面构建链（`build_windows.ps1`）只做编排，不再写业务逻辑。

## 13.8 发现六：更新说明把 Markdown 原样塞进面板（已修）

`release.yml` 里是 `--notes "$(head -30 CHANGELOG.md)"`。大屏的更新面板用
`textContent` 渲染，换行会塌成一段，于是老师看到的是：

```
# 更新记录 老师能直接感知到的变化写在这里；内部重构不列。 ## 0.3.27 — 2026-11-22 - **右下角菜单里…
```

改成 `--notes-file CHANGELOG.md`：工具取第一节、去掉 `**` `` ` `` 与链接记号、
条目用「；」连起来、超长在最近的「；」处截断，再以安装包版本作前缀。
产出变成一句话：`0.5.2：右下角菜单里「深色」前面有空缺：…`。

线上那份也已经换掉（只换 `notes`，签名与 URL 沿用 Release 上的原件，否则与线上包对不上）。

## 13.9 发现七：更新源里有一个必然失败的地址（已删，2026-11-23）

`tauri.conf.json` 的 `plugins.updater.endpoints` 第二项曾是
`https://classbeat.example.com/update/latest.json`——占位域名，永远连不上。
第一个源（GitHub）通的时候它不会被用到；GitHub 被墙时它会白等一次超时。

**2026-11-23 处理：删掉这一项**，只留 GitHub 的那个源。理由：占位域名没有任何
接上真源的计划，而它每次检查更新都实打实多等一次超时；真要有校内加速源，
加回来是一行 JSON 的事。

副作用：`desktop/docs/10-验收实测-A到E.md` 里 E4「更新源不可达时只告警」的实测
前提变了（当时靠"两个 endpoint 都够不着"制造断网）。要做同样的验收，得断网跑，
或者临时把 endpoint 指到一个不存在的地址。记录不改——那是当时的实测。

## 13.9b 发现八：跨零点的消息会被大屏藏起来（已修，CI 抓到的）

把 e2e 的被测服务换成 Rust 之后第一次跑 CI，有 6 条红：都是"手机发一条，屏上应该
出现"。原因不在 Rust 服务，而在页面：

- 消息的到期时间只存到分钟。`23:55` 发 10 分钟 → `until = "00:05"`；
- 页面 `visible()` 用 `nowHM() >= msg.until` 比字符串，`"23:55" >= "00:05"` 为真，
  于是当场判成"已过期"，屏上什么都不显示；
- 服务端 `messages.rs::expired()` 早就对 `00:00–06:00` 做了例外，所以服务认为消息
  还活着、页面却藏起来——两边打架，且只在 23:50–24:00 这十分钟里发作。

本地跑了十几轮都没撞见，是因为每次都在零点之后（`00:01` 发起，`until` 是 `00:11`，
字符串比较恰好成立）。已把判定抽成 `Remote._noticeExpired(until, now)`，与服务端
同规则，并在 `test_dom.js` 里加了 6 条断言（跨零点前/后、同日过点、未到点、无 until）。

## 13.9c 发现九：0.3.x 跨不到 0.5.x（已按"讲清 + 接住"处理）

真机反馈：装着 0.3.x 的机器点「检查更新」没有任何结果，升不到 0.5.x。查下来是
退役时删了仓库根的 `update.json`——而 0.3.x 的服务读的正是
`https://ghfast.top/https://raw.githubusercontent.com/sulengyin/ClassBeat/main/update.json`
（地址写在包根 `update-source.txt` 里）。文件没了 → 404 → 面板报
「**连不上更新服务器，请检查网络**」：把版本问题说成了网络问题。

根因不是漏删一个文件，是**两代形态在"怎么更新"这件事上没有交集**：

| | 0.3.x | 0.5.x |
|---|---|---|
| 更新器在哪 | 页面 + Python 服务，读 `update.json`（schema 1） | Tauri updater，读 Release 的 `latest.json` |
| 装法 | 下载 zip，**逐文件原位替换**程序文件 | 下载**签过名的 NSIS 安装包**并运行 |
| 凭据 | 每文件 sha256 | 整包 minisign 签名 |

所以"自动跨代"在技术上不成立——0.3.x 的更新器没有运行安装包的能力。

处理（2026-11-23）：

1. **`update.json` 恢复成跨代公告**（`schema: 2`）。0.3.x 的解析器会拒绝，
   并显示「更新清单格式版本是 2，这个版本的程序只认 1；请先手动更新」——
   比"网络不好"准确，老师也知道该干什么。用被删掉的旧解析器（`79cd068^`）实测过
   0.2.1 / 0.3.28 / 0.4.1 / 0.5.2 四个起点，行为一致。
2. **接住数据**：0.3.x 的数据在浏览器 `localStorage` 里，不在文件夹里，所以只能
   「导出设置 → 导入设置」。向导原来要到第 4 步才有导入入口，且第 1 步强制先填班名
   ——现在第 1 步直接给「导入旧设置 JSON」，导完自动跳到最后一页。
   （`Store.importAll` 是现成的，跨代没有另写一套保证逻辑；导出格式
   `rhythm-config/v1` 从 0.1.0 起没变过。）
3. **文档**：`docs/跨代升级-0.3到0.5.md` 写清为什么断、三步怎么做、会看到什么提示。

**没做的事**：出一个 0.3.29 桥接包，用旧更新器把页面换成带下载按钮的版本。
它能把老师"自动送到下载页"，但跨代那一下仍要人点安装包；代价是往老形态里再塞一次
未验证的自动更新（2026-11-19 就因清单与白名单口径不一致让所有自更新卡死过）。
收益与风险不成比例，不做。理由写在文档里，免得以后有人以为是漏了。

## 13.9d 发现十：同一件事被三处各自回答（已修，2026-11-23）

真机反馈两条，症状离得很远，根因是同一个：

> 值日岗位里选了某个学生，大屏却显示「待定」。
> 上传课表后改课务，下拉换了科目却带不出老师。

### 岗位「今天归谁」：三套字段，谁先命中听谁的

`role` 上能回答这个问题的地方有三个：`people`（指定人员）、`groups`（A/B 组）、
`peopleMap`（按星期）。旧代码是三段 `if`，顺序写死：

```js
if (role.groups)     return 组，没定组就 null;
if (role.rotation)   return status 不是 confirmed 就 null，否则查 peopleMap;
return role.people || [];      // 永远排在最后
```

于是：老师在面板里亲手指定了人，写进 `people`，但只要配置里还留着 A/B 组或轮换表
（样例数据里全都有），这次指定就被忽略；`rotation.status` 没确认时，`peopleMap`
里明明写了今天是谁，也一律判成未知。第二层是显示：`rhythm.js` 把同组合并成一条，
**任一条没排人就整组「待定」**，于是排好的人一个也看不见。第三层是入口：
「长期固定」按钮只对 `!groups && !peopleMap && !rotation` 的岗位出现——真正需要它
的轮换岗位反而没有，老师只能改今天，第二天又变回待定。

改法是把"归谁"收成一个入口 `resolvePeople`，候选源按**具体程度**排队
（指定人员 > 轮换到的那组 > 按星期表），空数组算"没指定"继续往下找，
返回 `[名单, 原因, 来源]`；组聚合改成"一个人都没有才算未知"，没排人的项记进
`pending`，点开详情才提示。入口侧所有岗位都能长期指定，轮换数据保留、
可一键恢复。`tools/build_day.py`（尺子）同步改同一套规则，golden 重新生成，
132 天逐字段对拍通过——这一步不能省，否则两份实现从这天起各说各话。

### 科目与老师：一张课表，两套名字

- `xlsxT` 把单元格里多段 `<t>` 直接相加。Excel 单元格内换行（富文本两段）会变成
  「语文王老师」，识别器再把整串当科目——下拉里多出一个假科目，选中也没有老师。
- 识别器只按空白切、且认定第一段是科目。老师写在上面（「王老师 语文」）就被当成科目。
- `setup.js` 有一张"常用科目表"，`edit.js` 有一套"同义归并组"，两边写法不同。
  识别认「道法」，下拉里叫「道德与法治」，老师选了后者就带不出老师。

三处一起改：新建 `app/subjects.js` 作为**唯一**科目词典（分组 + 别名 + 归一键 +
前缀识别），`setup.js` 与 `edit.js` 都只调它；课表格子的拆分改成"认内容"——
能认出科目的段是科目、剩下的才是老师，认不出时退回旧规矩（不比原来差）；
课务弹窗按归一键去重、老师做成可点候选、并加了「以后都改」（写进 `schedule.entries`，
同时清掉那节的当日覆盖，否则旧覆盖会继续盖住新配置）。

### 这一节留下的规矩

**同一个问题只能有一个入口。** 判断标准很朴素：如果两个地方都在回答同一个问题，
它们迟早给出不同答案，而症状会出现在离问题很远的地方（选人被无视、换科不带老师）。
这次动的三处（岗位归谁、科目词典、课表→老师的映射）都是这个形状，
下一处再出现时按同样方式收。

## 13.9e 发现十一：「人」没有唯一表示，于是每个读它的人各猜一遍（已修，2026-11-23）

### 三个症状，一个根因

老师报的是三件事：分组里的姓名还剩 `[object Object]`、更新后分组像是丢了、
「选了人屏上却待定」。上一版按症状逐个加兜底——给 `personNameOf` 修了递归深度的
bug、给大屏加了"对象不上屏"的过滤。修完症状确实少了，但**一周后同样的东西又冒出来**。

复盘时把「人」这个实体在代码里的所有形态列出来，根因才露出来：

| 同一件事 | 系统里有几种答案 |
|---|---|
| 一个人的写法 | 5 种：`"张三"`、`{name}`、`{id,name}`、`"s01"`、`"name:张三"` |
| 「取人名字」的代码 | 5 份：`store.personNameOf`、`schedule.nameOf`、`setup.nameOf`、`edit.nameText`、`screen.personName` |
| 「这岗位今天归谁」的代码 | 5 处：引擎 `resolvePeople`、`applyOverrides`、`rolePeopleNow`、`renderDuty` 的摘要、`groupDefs` 的内联逻辑 |
| 配置块清单 | 2 份：`Store.CONFIG_BLOCKS` 11 项、`Runtime.config()` 手写 8 项 |

第 3 行最要命：`rolePeopleNow` 的顺序是 `people → peopleMap → groups`，引擎是
`people → groups → peopleMap`。同一个岗位，面板说"按星期的那个人"，大屏说"A 组的
那个人"——老师看到的就是"我选的被吞了"。

### 死锁：进得去、出不来、回不去

真正的机制是四条路拼起来的一个闭环：

```
写入（patchConfig / patchDayOverride 不清洗）  → 脏数据进得去
导出（exportAll 原样吐）                       → 脏数据被固化进备份
导入（importAll 用 typeof g.name !== "string"）→ 能救的整份拒绝
清洗（sanitizeConfig 排在判死之后）            → 永远轮不到执行
```

实证（三个探针，不是推测）：

- 本机存一个组名是对象的组 → 点导出 → 把这份文件再导入 → `ok:false`，
  「设置里的「人群组」格式不对」。**程序自己导出的文件，自己导不回来。**
- `importAll` 导入含对象 `people` 的 `overrides`：一句校验都没有，对象原样落库。
- `saveGroup({source:"role", …})` 返回「组名和成员都要有」——明明都有。

还有一条更隐蔽的**腌毒链**，解释了"为什么更新好几轮还有残留"：

| 步 | 位置 | 发生什么 |
|---|---|---|
| ① | `edit.js` `(e.teacher \|\| "").trim()` | teacher 是对象时直接抛 TypeError，整块改课务打不开 |
| ② | `h("span","t",b.teacher)` | `textContent = 对象` → 屏上就是 `[object Object]` |
| ③ | `tea.value = b.teacher` | 输入框里已经填着这串字 |
| ④ | `tea.value.trim()` 存进 overrides | 老师一点「只改今天」，**显示故障变成合法数据** |

每更新一次、老师每点一次确定，就腌进去一条。所以"洗了好几轮还有"是必然的——
不是没洗净，是新的还在不断腌。

### 修法：三道闸门，不是五个补丁

1. **写闸门**（`store.js` 的 `cleanRoleOne / cleanGroupOne / cleanOverride / cleanConfig`）。
   凡是落进存储的「存人字段」一律先过它。清洗成了写入口的固有属性，不再靠
   schema 版本号触发——版本号只能洗一次，闸门每次写都生效。
2. **先清洗再校验**。校验只查骨架（是不是数组、是不是对象），元素长什么样
   归清洗管。反过来的话，`cleanGroupOne` 明明能救的"组名是对象"会被
   `typeof !== "string"` 判死。
3. **唯一解析入口**。`Schedule.resolvePeople` 导出来，编辑面板直接调它，
   `rolePeopleNow` 不再自己算一套。`nameOf` 收成 `Store.personNameOf` 一份；
   引擎保留的那 8 行是「脱离 UI 也能跑、要与 Python 对拍」的最小依赖，
   注释里写明它不参与写路径、不是第二套规格。

### 键的选择：姓名，不是 id

组员原来存 `s01`。查下来这个 id 是**人在 `students.json` 里手写编的**，系统不生成、
也不保证跨文件稳定：换一份名单就重新从 `s01` 排；老师"修正名单"时新加的人干脆
没有 id；同名两个学生在 `byName` 里只留最后一个，id 还会对错人。

**它是外部输入的人工编号，却被当主键用，而主键该有的约束一条都没有。**
改成姓名为主键、id 降级为别名；旧编码在启动时幂等转换一次（`fixGroupKeys`）。
编码三种都还能读，导出格式 `rhythm-config/v1` 一个字没动。

### 这一节留下的规矩

1. **一个实体只能有一种内部表示**，其余写法在入口归一，不在每个消费点各猜一遍。
2. **校验查骨架，清洗管元素**。两者顺序反了，就会把能救的数据判死。
3. **清洗是写入口的属性，不是一次迁移事件**。靠版本号触发的清洗，只洗过去，管不了将来。
4. **主键要选"用户认的那个"**，不是代码里顺手拿到的那个。id 顺手，但它是别人的编号。
